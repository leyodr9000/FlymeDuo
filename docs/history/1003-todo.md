## 1. 需求 A：环外网络类型标签的左右边距

### 现状
标签的水平间距**只有一个硬编码常量**：`app\src\main\java\io\github\yixing233\hyperduo\TrioHooks.java:133`

```java
/**
 * Gap between the battery view and the out-of-ring network type label.
 *
 * <p>Small on purpose: the label is drawn where MIUI's own {@code mobile_type}
 * tag used to sit, immediately left of the battery, and the whole status bar
 * row is only as tall as the icons.
 */
private static final float OUT_LABEL_GAP_DP = 2f;
```

它经 `outLabelGap()` 换成像素，有**两个消费者**。所以现在左右边距**强制相等**。

### 关键：LTR / RTL 下「左/右」分别指哪条缝
条带（strip）在 LTR 下的物理排布是：

```
[环外标签] --缝1-- [环外信号读数] --缝2-- [电池图标/原生图标行]
```

- **缝1 = 标签的右侧边距**（标签与紧挨它右边那个视图之间的空隙）
- **标签的左侧**朝外，对着原生图标行；标签单独存在（没有环外读数）时，`reserveOutRingStrip` 里的 `2 * gap` 就是「左边缝 + 右边缝」两条。
- **RTL 下整行镜像**：标签翻到锚点右边，于是「左侧边距/右侧边距」的物理方向互换。

> 写代码时**必须把这段语义写成注释**，否则 RTL 分支会被后人改错。

### 要改的位置（逐处）

**(1) `placeOutTypeLabel(ViewGroup container, View label, View anchor)` — `TrioHooks.java:2077-2126`**

唯一左右有别的一行在 `:2088`：

```java

        container.getLayoutDirection() == View.LAYOUT_DIRECTION_RTL;      // :2086-2087
```

```java

// RTL: 标签在右，与锚点之间留的是「左侧边距」

```

其余不动：`:2089` 垂直居中、`:2094-2103` 水平 clamp 进容器、`:2104-2113` 垂直 clamp、`:2114 label.layout(...)`、`:2122-2125` 超级岛位移。

**(2) `private static int outLabelGap(View container)` — `TrioHooks.java:2129-2132`**

```java

    final float density = container.getResources().getDisplayMetrics().density;

```

这就是本项目的 **dp→px 先例**（`outSignalSize` 也走 `getDisplayMetrics().density`）。要拆成两个（左/右），或改成一个带方向参数的 helper。

**(3) 第二个消费者：`reserveOutRingStrip(ViewGroup container)` — `TrioHooks.java:2573-2594`**


**(4) `refreshOutTypeLabel(ViewGroup iconContainer)` — `TrioHooks.java:1798-1866`**

这个函数在 `MiuiStatusIconContainer.onLayout` 里跑，**只能 relayout、绝不能 measure**。`:1839` 用

## 2. 需求 B：环外信号的上下 + 左右位置

### 现状
`OutSignalView`（`TrioHooks.java:2277-2304`，`private static final class OutSignalView extends View`）由模块自己 `addView` 进电池容器（`createOutSignal` `:2446-2456`，两轴 WRAP_CONTENT）。**关键事实：读数视图和标签共用同一个放置例程** —— `updateOutSignal` 的 `:2513` 是

```java
placeOutTypeLabel(container, view, anchor);   // 把读数视图自己当作 label 传进去
```

而标签自己的锚点是 `labelAnchorIn(container, anchor)`（`:2556-2562`：有可见的 `OutSignalView` 就返回它，否则返回 meter）。⇒ 布局顺序是「先把读数放在 meter 左边，再把标签放在读数左边」。

环外信号的实际绘制在 `TrioRenderer.drawOutSignal(...)`（`TrioRenderer.java:692-724+`）：

```java
final float scale = Math.min(width / inkW, height / TrioGeometry.STACK_INK_H);  // :705
final float x0 = (width - inkW * scale) / 2f;                                   // :710
final float baseline = (height - inkH * scale) / 2f
        + TrioGeometry.STACK_BAR_H[columns - 1] * scale;                        // :713-714
```

配套：`outSignalHeight(int sizeDp, float density)` `TrioRenderer.java:656-661`（`Math.max(1, Math.round(sizeDp * density))`）、`outSignalWidth(int height)` `:667-673`。

### 两条实现路径（必须二选一并写清理由）
- **路径 A（布局层给视图加偏移）**：在 `placeOutTypeLabel` 里给 `left` / `top` 加偏移，或在放置之后 `setTranslationX/Y`。
  - 好处：读数与标签共用例程，偏移天然参与 strip 计算。
  - 坑：`placeOutTypeLabel` 已经在用 `setTranslationX(-islandShiftPx(container))`（`:2122-2125`）做超级岛位移，**水平偏移若也走 translationX 就会互相覆盖**，必须合成成同一个值。
- **路径 B（在 `drawOutSignal` 里改 `x0` / `baseline`）**：只动画布内的居中偏移。
  - 好处：不碰布局、不碰 translation、不和超级岛打架。
  - 坑：视图的**测量尺寸/占位不变**，偏移后可能画出视图边界（会被裁掉或与邻居重叠）；且 `TrioPreviewView.drawOutSignal`（`TrioPreviewView.java:253-283`）也要跟着改，否则预览骗人。

**建议**：水平偏移走**布局层**（这样标签锚在 `anchor.getLeft()/getRight()` 上会自动跟着读数走，两者不会脱节），垂直偏移走 `top` 或 `translationY`。无论选哪条，`placeOutTypeLabel` 的签名会变 → **会打破工装的硬 pin，见 §5**。

### 取值范围（待定，建议）
`-12 … +12 dp`，默认 `0`，两个键（`out_signal_offset_x_dp` / `out_signal_offset_y_dp`）。

## 12. 1.6.1：环外信号「位置」改「边距」（用户报告，已修）

**用户原话**：「环外信号现在存在占位问题，现在不占位了，会悬浮在其他图标上方，似乎是调节的参数
导致的，应该不用位置来做调节了，而是边距」。诊断完全正确。

### 12.1 根因

1.6 的需求 B 把读数调节做成两个自由**位移**（`out_signal_offset_x_dp` / `_y_dp`），在
`placeOutTypeLabel` 的 clamp 之后加到 `left`/`top`。但 **strip 的占位只看
`getMeasuredWidth()`**（`reserveOutRingStrip`），位移不改宽度、也不参与占位计算 ⇒ 调大后读数
滑出为自己预留的空间，直接画到邻居图标的上层。

**通用结论：这条线上的任何调节都必须是「边距」，不能是「位置」。** 状态栏靠「预留一条空隙」给
元素让位；边距是被预留的那个数字（所以原生图标会跟着让位），自由位移没有对应的让位动作。

### 12.2 改法

- `Prefs.KEY_OUT_SIGNAL_MARGIN = "out_signal_margin_dp"`，int dp，默认 **2**（= 原来写死的
  `OUT_LABEL_GAP_DP`，升级不变样），范围 `0..16`。两个旧位移键**删除、不迁移**（只存在了一天、
  默认 0，绝大多数安装没写过；语义也无法一一映射）。
- `TrioHooks`：`outSignalOffset()` → `outSignalMargin()`；`placeOutTypeLabel` 第三参由
  `(offsetX, offsetY)` 改为**单个 `gap`**（「这个视图与锚点之间的缝」），三参重载内部取
  `outLabelAnchorGap()` 给标签用；`reserveOutRingStrip` 改为用各自的缝求和（读数是
  `signalGap`，标签是朝锚点那条缝 + 独占时的外侧缝）。**默认值下 total 与 1.6 之前逐项相同**
  （读数 +2、标签 +2；标签独占时 +4），所以出厂外观不变。
- **垂直调节取消**：行内没有可预留的纵向空间，纵向位移只能是「压到别的东西上」，读数一律垂直居中。
- 预览第 8 格改为「读数到格子右边缘（= 电池位置）的距离」，窗口宽 = 读数 + 滑块上限，整个量程
  都在格内。
- 文档：README 尺寸表、DEVELOPMENT 键表与「信号：环内与环外堆叠」/「网络类型」两节、
  SWITCHES-REVIEW 键表 + §6.9 二改写 + 新增 §6.10、新建 `release-notes-1.6.1.md`。

## 17. 第十六轮（v1.6.6）：充电超级岛出现时的接管（用户需求）

`MiuiStatusBatteryContainer.setIsHideBattery(true)`：容器对 mBattery **跳过测量与占位**（原生图标

的电池坐标上。

**实现**（提交 `040ed37`）：hook 组 10 拦 `setIsHideBattery`，值记入
`TrioState.sIslandHideBattery`（全局 volatile），翻转时走 `applyConfigChange` 同形的反应

`!islandHideBattery()`）；Wi-Fi 槽交还（`foldedSlots` 里 wifi 折叠要求 `!islandHideBattery()`）；
信号无条件按环外读数（mobile 槽无条件折，`syncOutSignal`/`requestOutSignalSync` 门放宽为
`stackedOut() || islandHideBattery()`）。环外标签锚链 `labelAnchorIn` 优先取读数——岛下读数必在，
锚点自然有效。岛收回同一反应还原。工装 pin `if (a.foldsMobile())` 按本意放宽为允许
`|| islandHideBattery()` 尾缀。

## 18. 第十七轮（v1.6.7）：修 1.6.6 的岛态坐标错误

**用户报告**（附截图）：「状态栏的充电超级岛适配逻辑……问题不小」——截图里环外读数与原生网速
（`22 KB/s`）叠在一起。

**根因**（反编译逐行确认）：`placeOutTypeLabel` 锚 `meter.getLeft()`。正常态它恰等于图标行右界
（容器把行右界算作「容器右 − paddingEnd − 电池宽」，电池正布局在那里），所以一直对；**岛上这个
等价被破坏**——`MiuiStatusBatteryContainer.onMeasure` 不再累加电池宽、`onLayout` 的行右界 `i7`
也不再减电池宽（行右移让位），但电池视图**仍按原位布局、只被 `updateVisibility$6()` 设
`INVISIBLE(4)`**（不可见但仍占位；只有 homeBlock/极简走 GONE）。于是读数落在比行末**左移一个
电池宽**处，压在右移过来的原生图标上。

**修法**（提交 `18a2050`）：横向基准改取 `iconContainerIn(container)` 的 `getRight()`（RTL 取
`getLeft()`）——两态都正确，且正是 `reserveOutRingStrip` 预留 padding 收尾处；取不到时退回原
anchor 边。两态下该边缘与 meter 左缘**相等或正好差一个电池宽**，故正常外观逐像素不变。垂直基准
仍取 anchor。

**规则收紧**：岛只改变信号**画在哪里**、不改变用户**是否要它**。`foldedSlots()` 的 mobile 折叠
条件**还原为纯 `a.foldsMobile()`**（1.6.6 的 `|| islandHideBattery()` 会在用户关掉移动信号时凭空
折掉原生图标）；新增 `outSignalWanted() = stackedOut() || (islandHideBattery() && foldsMobile())`
作为 `syncOutSignal`/`requestOutSignalSync` 共用的唯一谓词。

**v1.6.7 已发布**：tag `v1.6.7` 指向 `a6a3d87`；主仓 `…/download/v1.6.7/HyperDuo-1.6.7.apk`、
模块仓 `…/download/10607-1.6.7/HyperDuo-1.6.7.apk`；**3,092,164 B**，`versionCode=10607`，
`sha256 = b12b6b15…4904724bfd`。**仍未上机**（设备离线）——上机要点：插电出岛时读数贴在图标行

## 23. 第二十一轮（v1.6.10）：环外标签与读数重叠（用户报告，已修）

**用户原话**：「现在的尺寸是正常的，只是网络类型和移动信号重叠了」，并附实机截图：环外模式下
「5G」标签画在堆叠信号读数上面，两者完全重合。

### 23.1 根因：标签被放到和读数同一个参照边上

`labelAnchorIn()` 早就写对了——有读数时返回读数、没有时返回电池表——**两处调用点也都链了它**。
问题在 `placeOutTypeLabel()` 内部：它拿到锚点后，只要原生图标行已测量（**实机上每帧都是**），
就把水平参照**强制换成图标行自己的边缘**，把传进来的锚点丢掉。而读数自己的摆放用的**也是**这条
边缘，于是两者的右边缘落在同一个像素上，标签直接叠在读数上。

也就是说：**「链对了锚点」这半个修复在 1.6.6 就有了，但「按锚点摆放」这半个一直没落地。**

### 23.2 改法

`placeOutTypeLabel()` 的水平参照按「这个视图实际靠着谁」分派：

| 视图 | 何时 | 参照边（LTR） |
|---|---|---|
| 读数 | 总是靠着电池 | 图标行的右边缘（1.6.6 的岛修复，**不变**） |
| 标签 | 有读数时靠着**读数** | `reading.getLeft()` |
| 标签 | 无读数时靠着电池 | 图标行的右边缘 |

链读数时**要求读数已 `getWidth() > 0`**：刚测量还没 layout 的读数帧是空的，照它链会把标签甩到
容器最左边一帧；此时退回图标行边缘（就是读数出现前它站的地方），下一帧再链上。

`reserveOutRingStrip()` 还藏着同一处 bug 的另一半：它**只在没有读数时才把标签的外侧边距计进预留**
（当时的推理是「有读数时两视图之间的缝已经算过内测那条了」）。但外侧边距**两种情况都在画**——
那是标签挡住原生图标的另一侧——所以有读数时预留宽度**比实际占的宽度窄**，把
`out_type_margin_left/right` 调大根本不生效。现在两条边距一律计入；默认值下预留宽度与之前逐项
相同，出厂外观不变。

### 23.4 图标反色（同一轮内用户报告，已修）

**用户原话**：「现在是图标反色问题」，附实机截图：浅色桌面上，模块画的三合一与「5G」标签是
**黑色**，而紧挨着的 MIUI 原生图标（蓝牙、网速文字）是**白色**。

**根因（设备日志直接坐实）**：`hookIconTint` 把听来的颜色写进**一个全局槽 `sBarInk`**，
`TrioState.foreground()` 再全局读它。但屏幕上有**四行**电池容器（状态栏 / 锁屏 / 控制中心 /
QS 头部），系统在**同一帧**把它们染成**相反**的颜色。实机日志里两簇签名反复出现：

```
tint: useTint=true tint=e6ffffff light=e6ffffff dark=e6ffffff intensity=0.0 -> bf000000
tint: useTint=true tint=bf000000 light=e6ffffff dark=bf000000 intensity=1.0 -> bf000000
```

第一行是**宿主自己**要白色（`e6ffffff`），但 `->` 解析出来是**黑色**——因为第二行那种
「要黑色」的行刚刚把全局槽覆盖了。谁最后染色谁说了算，于是总有一行画反。

**改法**：`sBarInk` 单槽删除，换成 `ROW_INK`（`WeakHashMap<View, Integer>`，键是**该图标所属行
的电池容器**）。`hookIconTint` 用 `chain.getThisObject()` 找到被染色图标所属的行再写；
`TrioState.foreground()` 改读 `TrioHooks.rowInk(TrioHooks.rowOf(host))`。某行还没被染色时仍返回
0，照旧落回宿主自己的 `mUseTint/mTintColor/...` 字段链，兜底逻辑未动。

**验证**：装机（`Success`）→ `killall com.android.systemui` → 截图
`.tmp/ink_fix.png` / `ink_fix_bar.png`：整行墨色一致，反色消失。**用户确认「正常了」**。
工装新增 5 条 pin（按行存、行查找、按行读、旧全局槽必须不存在），逐条对 `HEAD` 源码跑过**全部
命中旧代码**；`simcheck` 的 `TrioHooks` 桌面替身补了同名的两个方法以便 `TrioState` 编译。
五工装全部 `exit 0`。

## 24. 第二十二轮：合并 PR #18（Wi-Fi 实时状态）+ PR #17 的处置

### 24.1 PR #18 已合并（`cff0c2e`，作者署名 L-aros）

## 29. 第二十七轮：状态栏性能读数（充电功率 / 电池温度）

### 29.1 本轮做了什么

- **两个新的布尔键**：`Prefs.KEY_PERF_POWER = "perf_power"`（充电功率）、
  `Prefs.KEY_PERF_TEMP = "perf_temp"`（电池温度），默认都是 `false`，没有上下界。两个键都是
  **全新名字**：框架对陌生键不做任何类型转换，旧版本读到它们只会当作不存在的键，所以新增不需要
  迁移代码；反过来，名字一旦发布就不能再改（改名等于换键，用户的设置会静默回到默认）。
- 对应地往 `TrioSettings` 加了 `perfPower` / `perfTemp` 两个 public boolean 字段（含
  `applyKeyFrom` 分支、`fromBundle` / `toBundle` / `equals` / 拷贝构造），往 `TrioAppearance`
  加了 `perfPower` / `perfTemp` 两个 `public final boolean`，以及谓词
  `perfAnywhere()` = `perfPower || perfTemp`。
- **两个开关共用同一个视图**：`TrioHooks.PerfLabel`，一个挂在电池容器（`batteryContainerOf(host)`）
  上的 `TextView`，位置就在已有的环外类型标签与环外读数旁边。共用一个视图而不是各挂一个，是因为
  两项的可见性可以独立：只开功率就只有功率、只开温度就只有温度、两个都关整块视图才摘掉
  （挂载门就是 `perfAnywhere()`，另加总开关 `a.glyph`）。
- **文本按段拼**（`TrioHooks.perfText`）：功率段只在 `TrioState.sChargingAttached` 为真时出现，
  温度段只要不是 `TrioState.TEMP_UNKNOWN` 就出现，两段之间用一个换行符 `PERF_BREAK` 相接——
  **一项一行**（见 §29.4，这是用户追加要求后改的；最初版本用的是空格）。
- **采样器 `BatteryPresence.java`**（形状照抄 `WifiPresence.java`）：注册一个粘性的
  `ACTION_BATTERY_CHANGED` 接收器，从粘性 intent 里读 `EXTRA_PLUGGED` / `EXTRA_STATUS` /
  `EXTRA_TEMPERATURE`（单位是十分之一度）/ `EXTRA_VOLTAGE`（mV），电流取自
  `BatteryManager.getIntProperty(BATTERY_PROPERTY_CURRENT_NOW)`（单位 µA），再在 SystemUI 里
  自续一个 3 秒的看门狗。`BatteryPresence.start(sContext)` 由 `TrioState.attachContext` 挨着
  `WifiPresence.start(sContext)` 调用。
- 读数发布为三个 `TrioState` 静态量：`sChargingAttached`（boolean）、`sChargePowerW`（float）、
  `sBatteryTempC`（int，未知时是新的哨兵值 `TEMP_UNKNOWN`）。
- 设置页两行开关（各一个 `SwitchPreference`，`enabled = a.glyph`），字符串在
  `strings.xml` 的 `perf_power_title` / `_summary` 与 `perf_temp_title` / `_summary`。
  这一对是**只有 Hook 侧读**的键：渲染器与预览都不看它们。

### 29.2 决策与理由

- **为什么用广播 + `BatteryManager`，而不是直接读 sysfs / health HAL**：模块跑在
  `android.uid.systemui` 里，sysfs 的电池节点与 health HAL 对这个 uid 都是关着的，
  只有 `ACTION_BATTERY_CHANGED` 与 `BatteryManager.getIntProperty` 这条公开路径能用。
  粘性广播同时还解决了「刚起来时没有读数」的问题——注册后立刻能拿到最后一次广播的值。
- **功率是电池自己的电流 × 电压，不是充电器协商的最大档位**：协商值在电量爬升时几乎不动，
  而用户想看的正是「现在还充进去多少瓦」。电池电流会随电量升高逐渐变小（恒压阶段尤其明显），
  这才是真实速率。
- **瓦数 clamp 在 0，但「问不出来」是另一个答案**：满电时电池电流是**一个小负数**（在向外漏电），
  直接相乘会得到负功率。负瓦数没有意义，所以钳到 0。而 `getIntProperty` 对不支持的属性返回
  `Integer.MIN_VALUE`、没有电压的设备 `EXTRA_VOLTAGE` 是 0——这两条**不是** 0，是新的哨兵
  `TrioState.POWER_UNKNOWN`（`Float.NaN`）。早先版本把它们也折成 0，会在温度旁边显示一个
  「0.0W」，正是本条要避免的那种假读数（§29.7 修正）。
- **没接充电器时功率段整段消失，而不是显示 `0W`**：`0W` 挨在温度旁边会被读成「读数坏了」，
  而它实际只表达「没在充电」。温度与充电器无关、照常显示——这条不对称正是两项要分成两个开关的
  原因。
- **显示格式**（`powerText`）：不足 10W 保留一位小数（`6.4W`），10W 及以上取整（`18W`）——
  两位数的瓦数上小数位没有信息量。整数运算拼串、不走 `String.format`，省掉 `Locale` 问题
  （逗号小数点会占更宽）。
- **温度取整**：整摄氏度足够，且读数只有几个字符宽。degree 符号在源码里写成 `"\u00B0C"`，
  保持 `TrioHooks.java` 全 ASCII。
- **字号复用「环外网络类型字号」（`out_type_size_dp`）作为基准，不给自己加滑杆**：它们与环外类型
  标签是邻居，用同一个键才能对得齐。再加一个滑杆只会多一个要解释的旋钮。两项都开时在这个基准上
  按图标高度自适应缩小（§29.5）。（**第十四轮补了一条**：仍然以环外字号为基准，但在它之上加了
  「读数整体尺寸」`perf_scale_pct` 这个整体乘数，见 §30.2(d)——它不是第二个基准，所以本条的
  「用同一个键对得齐」依然成立。）
- **新的环外视图加入 `reserveOutRingStrip` 的那一条求和**，而不是给自己单独预留一段宽度：
  strip 是唯一能让原生图标跟着让位的机制，各视图各撑一次 padding 会互相挤掉（第 12 轮已经踩过
  一次）。锚链上 `labelAnchorIn` 先看可见的 `PerfLabel`，没有才退回 `readingAnchorIn`。
- 挂载/摘除照抄另两个环外视图：只走 posted 路径（`settle` 是从 `onLayout` 里调的，那里不能
  `addView`），用 `instanceof PerfLabel` 当标记（不用 `WeakHashMap`），`restoreNative` 时摘掉，
  前景色走 `applyOutRingInk`，另外在 `settle` 里补一次 layout 安全的 `refreshPerfLabel`。

   「按下限封底」那条分支，而不是 §29.5 离线校核算出的 36.9px；两条读数各自一行、没有溢出，
   这是 §29.5 与 §29.6 都已上机的证据。§30.3 里仍然挂着的是**两条整体尺寸滑杆**没上机。

### 29.5 追加：组合字号自适应（用户要求）

用户追加要求「组合的字体需要小一些」，澄清为「确保两行能在一个图标高度中放下」＋「适配」，
即不是固定乘一个系数，而是**按图标实际绘制高度反推字号**。改动仍全在 `TrioHooks.java`
的 `performance readout` 区块：

- 新增 `private static final float PERF_MIN_SIZE_RATIO = 0.6f;`（缩放下限，防止一帧未测量完的
  host 把读数压到看不清）与 `private static final Paint PERF_PROBE = new Paint();`。
- 新增 `perfLines(String)`（数 `PERF_BREAK`）与 `perfLineHeight(float size, int weight)`
  （在 `PERF_PROBE` 上取 `descent - ascent`）。**用探针而不是 view**：要决定的正是这个字号本身，
  从 view 上读会让结果依赖 view 是否已经被赋过值。
- 新增 `perfTextSize(String text, View container, View host)`：一行返回 `outTypeSizePx(container)`；
  两行时取 `TrioRenderer.inkScale(host.getWidth(), host.getHeight(), a.rect)`——**与 `drawInto`
  给画布用的完全同一个适配系数**——乘以 `INK_H`（矩形样式用 `RECT_INK_H`）得到图标真实绘制高度，
  再除以行数换回字号：`base * (icon / lines) / lineHeight`，最后
  `Math.max(base * PERF_MIN_SIZE_RATIO, Math.min(base, size))` 收口。
- `updatePerfLabel` 的 `final float size = outTypeSizePx(container);` 改为
  `perfTextSize(text, container, host)`；`refreshPerfLabel` 的重同步比较
  `perf.getTextSize() != outTypeSizePx(container)` 同步改为
  `perfTextSize(text, container, host)`——**少了这一处，字号变了也不会重新同步**。
- `perfLineSpacing` 的文档改写：现在它通常返回 `1f`（字号已按图标高度自适应，
  下限未触发时两行合起来正是一个图标高），只在「行被摆得比字形还矮」（容器高度装不下两行）时才真正压缩行距。

**实测（`wm size` 1200x2670 / `wm density` 480）**：图标行 `x=1020..1115 w=96 y=37..108 h=72`
（那一段是环与光圈的墨迹；`INK_H = 117.5` 是**整个字形**的紧墨盒，含顶部指示与底部圆点，比环本身高）。
并排改两行后两行墨迹只有 39px，却占着 96px 的 view 盒——字号正是为此下调。

**离线数值校核（设备脱离 USB 后补做）**：容器与锚点取自模块自己的日志
（`container=491x88`、`anchor=407..491`，即环宽 84px；`base = out_type_size 14dp × density 3 = 42px`）。
`fit = min(84/117, 88/117.5) = 0.7179` 是宽度受限，`icon = 117.5 × 0.7179 = 84.4px`；
单行 `lineHeight(42) = 48px`（与两行时 `view=102x96` 一致）。于是
`size = 42 × (84.4 / 2) / 48 ≈ 36.9px`，远高于下限 `42 × 0.6 = 25.2px`，
两行盒高 `= 2 × 48 × 36.9/42 = 84.4px`，**恰好等于图标墨盒高度**，落在 88px 容器内。
即：`perfTextSize` 的定义使「两行合起来 = 一个图标高」在下限未触发时是恒等式而非近似；
一旦行高窄到下限 `PERF_MIN_SIZE_RATIO = 0.6` 接管，两行就会略微高过图标——这是刻意的取舍，
宁可略高也不缩到看不清。`perfLineSpacing` 是第二道防线，只在行本身比字形还矮时压缩行距。

### 29.7 独立复核后的修正

设备脱离 USB 期间，对未提交的改动做了两轮**互相独立**的对抗式只读复核（只读、不改文件）。
两轮都判**无 BLOCKER**、不崩溃，且**各自独立地**指出了同一个 MAJOR。以下按严重度记录修正。

**MAJOR —— layout 期的失效判定漏了行距。** `refreshPerfLabel` 的重同步比较只看可见性、文本、字号：

```java
if (perf.getVisibility() != View.VISIBLE
        || !text.contentEquals(perf.getText())
        || perf.getTextSize() != perfTextSize(text, container, host)) {
```

而 `perfLineSpacing` 读的是容器高度，而那一行不是固定高度——MIUI 收起状态栏时排成 88px、拉开控制中心后
变成 134px（`dumpsys window displays` 实测）——**这条路径上只有容器高度变了**，host 尺寸没变，
于是文本与字号都比得相等、不会 post 同步，上一帧按另一个行高算出的行距被留下。同族的
`refreshOutTypeLabel` 是比了自己的缩放项的，所以这是新漏的一处。
修正是补上第四个条件（`perfLineSpacing` 只读 paint 度量与容器高度/内边距，不写不 post，因此在
layout 回调里读它是安全的）：

```java
        || perf.getLineSpacingMultiplier()
                != perfLineSpacing(perf, text, container)
```

**MINOR 一并修掉：**

- **「问不出来」被折成了 `0.0W`。** `Prefs` 的注释承诺「没在充电时这一段消失，而不是显示 0W」，
  但 `perfText` 只判断了 `sChargingAttached`，而 `wattsOf` 把 `Integer.MIN_VALUE`／电压缺失折成
  `0f`——于是「接着充电器但平台答不出功率」会画出一个很自信的 `0.0W`。新增
  `TrioState.POWER_UNKNOWN = Float.NaN`，`wattsOf` 的两条不可用分支返回它，`perfText` 多判一项
  `!Float.isNaN(sChargePowerW)`；**真正的 0（满电、充电器停止推流）仍然显示 `0.0W`**，
  「满电时不闪断」的行为不变。
  - ⚠️ 这一项最初写成 `sChargePowerW != POWER_UNKNOWN`（复核意见也是这么建议的），**那是错的**：
    哨兵是 `NaN`，而 `NaN != NaN` 恒为真，这个门会把它本该挡住的哨兵自己放行，`powerText` 里
    `Math.round(NaN * 10f)` 得 0，画出来正是要避免的 `0.0W`。哨兵判等只能写 `Float.isNaN(...)`。
    这个错误是 `tests\battery-presence.ps1`（见 §29.8）抓出来的，不是读代码读出来的。
- **哨兵是 `NaN` 带来的连带问题：`publish` 的去重比较。** `beforeWatts != TrioState.sChargePowerW`
  在 `NaN` 上**恒为真**，会让答不出功率的设备每 3 秒无谓地 `invalidateHosts()` 重绘状态栏一次。
  改用 `Float.compare(beforeWatts, TrioState.sChargePowerW) != 0`（`NaN` 与自身比较相等）。
- **死字段**：`TrioState` 的实例镜像 `chargingAttached` / `chargePowerW` / `batteryTempC` 每帧从静态量
  抄一遍却无人读（读数走的是自己的 layout 刷新路径，直接读静态量）——已删除这三个字段与赋值。
- **`hashCode()` 与 `equals()` 不一致**：`equals` 含 `perfPower` / `perfTemp`，`hashCode` 不含。
  虽然全仓库没有任何地方拿 `TrioSettings` 做哈希（原注释也这么写），仍把两项折进去以保住契约。
- **文档把自适应说死了**：`PERF_MIN_SIZE_RATIO = 0.6f` 是缩放下限，触底时两行会略高于一个图标，
  而 `module-README.md` 与本文 §29.5 原文都写成「保证两行合起来仍是一个图标高」。已改为
  「下限未触发时是恒等式，触底时宁可略高也不缩到看不清」。
- **`docs\SWITCHES-REVIEW.md` 的键行引用行号写错**（`:3615`／`:3618`，且把 `perfAnywhere()`
  记成 `TrioHooks.java:3481`，那里其实是 `PERF_PROBE`）。已改为 `TrioHooks.java:3667`／`:3687`
  与 `TrioAppearance.java:312`（源码后来又改过注释，这里已按最终行号对齐）。
- **注释里对框架的描述是反的**：`setLineSpacing` 缩放的是**第一行之后**的每一行，第一行保留全高；
  原文写成「layout 总是给最后一行全高」。算术（`aboveLast = room - lineHeight`）两行时数值不变，
  但描述已改正。另把 `PERF_PROBE` javadoc 里的 `TextPaint` 改为 `Paint`（字段就是 `Paint`）。
- **行距重同步的理由写反了方向**：补上第四个重同步条件时，注释与 `1003-todo.md` §29.7、
  `docs\DEVELOPMENT.md` 都把它说成「下拉控制中心把容器压短」。仓库自己的实测是反的——
  `docs\DEVELOPMENT.md:1017-1021`、`docs\SWITCHES-REVIEW.md:418`、`1003-todo.md:342` 三处一致记录

  「字号下限触底后剩下的空间不够」上——那才是它现在唯一真正会生效的场景。

**两轮复核都确认没问题、不必再查的**：`perfTextSize` 量纲正确（行高对字号线性）、四条退化路径都

### 29.9 第二个断言脚本：自适应字号与行距（`tests\perf-layout.ps1`）

脚本 **`tests\perf-layout.ps1`**（38 条断言，`PASS: 38 cases over perfTextSize, perfLineSpacing and
inkScale`；**第十四轮已扩到 48 条**，见 §30.1；**复核后再扩到 53 条**，见 §29.10），同样用正则把生产方法原样抽出来（`perfTextSize` /
`perfLineSpacing` / `perfLines` / `perfLineHeight` / `outTypeSizePx` 来自 `TrioHooks.java`，
`inkScale` 三个重载与 `typefaceFor` 来自 `TrioRenderer.java`），并从 `TrioGeometry.java` 与
`TrioHooks.java` 里**读出**四个墨框常量与两个下限（读不到就 `throw`，且断言它们严格落在 `(0,1)` 内）。

它锁住的核心命题是那条设计身份，而且是以**恒等式**而非「大概」的形式：

* `2 * perfLineHeight(size, weight) == inkH * inkScale(host)`（容差 0.05）——「两行合起来是一个图标高」；
* 单项读数无论宿主多小都保持基准字号（`lines < 2 || host == null` 的兜底）；
* 宿主小到装不下时**正好落在 `base * PERF_MIN_SIZE_RATIO` 下限上**；
* 三行比两行小；`rect` 样式的墨框更矮（114.4 < 117.5），所以同一宿主下取到更小的字号；
* 行距：单行恒为 `1f`、容器高为 0 恒为 `1f`、足够高恒为 `1f`、略矮则 `< 1f` 且不低于 0.72、
  且**挤压后正好等于可用高度**；容器的 `padding` 要从可用高度里扣掉；
* **把被否决的算法钉死**：断言 `multiplier != room / lines`（原来的做法把首行的整高摊到所有行上，
  栈比行还高）。这条反向断言是防止有人「简化」回那个更直觉但错误的写法。

**它抓到的两个 modelling bug 都出在垫片，不在生产代码**，但两个都值得记下来，因为都会让探针
「什么都没量却通过」：

1. `work\preview` 的桌面 `Paint` 垫片直接返回 AWT 的 **正** ascent，而 Android 的
   `FontMetrics.ascent` 是**负**的。两个方法都按 `descent - ascent` 算行高，正值代入后行高变成负数，
   于是 `perfTextSize` 和 `perfLineSpacing` 全部走各自的「量不出来」兜底分支——探针会全绿而实际
   一条算术都没走到。本脚本因此**不再复制**那个垫片，改为自己生成 `android/graphics/Paint.java`：
   `out.ascent = -fm.getAscent(); out.descent = fm.getDescent();`（`Typeface` 仍复制，保证字体族解析
   与预览工装一致）。
2. 即便修好符号，AWT 会把字号**取整到整点**，而 Android 的度量对字号严格线性；`perfTextSize` 拿
   基准字号的行高去除另一个字号下的尺寸，取整误差就让恒等式以 0.3px 假失败。垫片因此改成
   **在参考字号量一次再线性缩放**（`scale = textSize / REFERENCE`）。

事后的反向对照（照仓库规矩，只跑通过的那一边等于没有反例）**四次都成立**，每次都先用 `.bak`
回滚、事后核对源码与 `git status` 干净：

### 30.2 决策与理由

**(a) 字形滑杆为什么只能 60 – 100。** MIUI 给电池图标预留的框只有 **28dp × 20dp**，而那个框是系统
画的、模块改不动它。100% 已经等于系统允许的最大值，再往上调只会画到视野外面，**裁不裁由 MIUI 说了
算**——「要求得比盒子能装的更多」并不能让盒子变大。做 dp 滑杆同样绕不开这个框：dp 值最终还是要换算
回「占这个不归模块所有的盒子的比例」，所以直接做成百分比更诚实，也让 100% 有明确含义（= 系统允许的
最大值）。下界取 60 与读数的下界对齐，再小就没有实用意义。

**(b) 乘数为什么乘在 FIT 上，而不是乘在设计单位上。** 整块三合一几何是**同一个 120×120 的盒子**，
`drawInto` 先按样式选墨迹盒、再算一次适配、做一次 `translate` + `scale`。缩适配会让每一笔描边、
每条弧、每个数字按**同一比例**变化，而那次 `translate` 仍然把结果居中在同一个位置。若改成对设计单位
另做一次 `canvas.scale`，`Paint.setStrokeWidth` 收到的是设计单位下的常量，线宽与半径/坐标的缩放口径
就会分家——描边不会跟着半径一起变。

**(c) 缩放为什么必须只在适配系数这一处应用一次**（本轮避开的陷阱）。槽里的字形由 `drawState` 画，
而 `drawState` 走的就是上面那条**已经乘过 `glyphFit()`** 的路径。若交给 drawable 的 bounds 再按同一个
百分比缩一次，设置就被应用了两遍，字形会变成「缩小值的平方」。正确形态是 **bounds 就是 MIUI 给电池
图标的那个框 + 居中的小字形**：设置的语义本来就是「框不变、画小一点」，而不是「换一个更小的框」。
`GlyphDrawable.draw` 因此把 `getBounds()` 的宽高原样交给 `drawState`，不做第二次换算。
（第三十一轮之前这条记的是 `TrioOverlay.sync()` 刻意不碰 `glyphScale`——窗口路线已在 §33 整体删除，
但「只应用一次」这个判断不变。）

**(d) 读数滑杆为什么是「自适应之上的百分比」，而不是一个绝对 dp 字号。** 乘在自适应结果之上，两项
读数就仍然跟着图标高度与基准键 `out_type_size_dp` 走，用户调基准字号时这对读数不会被一条绝对尺寸
锁死在外。而且它**必须应用在 `perfTextSize` 的每一条答案上，包括单项读数与「量不出来」的兜底**：
只有一项读数打开时走的正是 `lines < 2` 那条分支，若滑杆只缩放组合态，单项时它就毫无反应，等用户
打开第二个开关时读数会突然跳一下——那才是真正的怪。应用在最后也让它保持「对布局的一次修正」，
而不是对布局的第二种意见。范围 60 – 150 比字形的宽、且允许超过 100，正是因为它乘的是一个**字号**，
不是一块被宿主框限死的绘制。

**(e) 两个键都用全新名字。** 框架对陌生键不做任何类型转换，一个键一辈子只有一个类型；沿用旧键名
就是换掉旧键的含义，用户的设置会静默错位。`glyph_scale_pct` / `perf_scale_pct` 之前没有任何键用过
这两个名字，所以新增不需要迁移代码；反过来，名字一旦发布就不能再改。

### 30.4 第三个断言脚本：整体尺寸到达画布（`tests\glyph-scale.ps1`）

§30.1 说字形滑杆「已用桌面探针实测」，那个探针在 `work\_scaleprobe\` 里——**`work\` 被 `.gitignore`
排除、不进版本库**，而且它只量了一个 `120×120` 宿主上的墨迹总数（`glyphScale` 100 → 5127、60 → 1948）。
一个不入库、只比两个整数、还是自己人写的临时件，随时会在清理工作区时被当垃圾删掉，删掉之后
`glyphFit()` 就退回「只有代码、没有证据」。于是把它升级成入库脚本 **`tests\glyph-scale.ps1`**（第四个
纯 JVM 断言脚本，17 条，`PASS: 17 cases over glyphFit, the uniform fit and the clamped bounds`）。

**为什么这一条必须数像素，而不能只查公式。** 前面三个脚本抽的都是**纯函数**（`wattsOf`、`perfText`、
`perfTextSize`），但「字形整体缩小」这个功能的风险不在公式里，而在**接线**上：`glyphFit()` 算得再对，
只要 `drawInto` 没有把它乘进那次 `canvas.scale`，用户就什么都看不到——而公式层面的断言对此完全无感，
它会心满意足地绿着。新脚本因此走**端到端**：用 `tests\shims` 的桌面垫片（真 `Canvas` 把
`save/restoreToCount/translate/scale/draw*` 映射到 Java2D），把**真 `TrioRenderer.drawInto`** 画进
`BufferedImage(120, 120, TYPE_INT_ARGB)`，再回读位图数**真正落笔的像素**，返回
`{count, minX, minY, maxX, maxY}`。断言的是「画布上发生了什么」，不是「函数返回了什么」。

**17 条断言的分工：**
- 默认值仍等于 `DEF_GLYPH`；`glyphFit()` 在 100 时是 `1.0`（用 `close(…, 1.0, 0.0)` 比，`eq` 收 `long`，
  直接传 `1f` 会 `错误: 不兼容的类型: 从float转换到long可能会有损失`）。
- 100 / 90 / 80 / 70 / 60 五档的墨迹数**逐档严格递减**。
- **墨迹面积随系数平方下降**（`small / full ≈ (60/100)²`，tol 0.03），**包围盒宽与高各随系数线性下降**
  （tol 0.02）。这两条才是「等比缩小」的证据：只有墨迹总数下降的话，一个「把细节熔掉、外框不动」的
  实现也能满足；面积按平方、外框按线性，才说明整块几何确实按同一比例缩了。
- 满档 `boxWidth(full) >= 120 * 0.97`（铺满它被测量的宿主）；最低档四边各留 ≥ 5px、且水平与垂直中心
  仍在 `59.5`（tol 3.0）。后者抓的是**「缩了但没重新居中」**：`translate` 若不跟着缩放走，图形会缩到
  角落去。
- **clamp 两端各渲染一次，与 floor / ceiling 的像素逐位相同**（`same(a, b)` 逐项比较五元组）——证明
  越界的存储值真的落回边界，而不是被截断成别的尺寸。
- 矩形样式（`STYLE_RECT`）单测一遍：满档与最低档各一次、`rectSmall[0] < rectFull[0]`、宽比同系数、
  四边留白。乘数只接进一种布局是很容易犯的错，环与矩形各测一遍才盖得住。

**四条源码契约钉**（像素能看出「变小了」，看不出「是在 fit 上缩的而不是在别处」）：`inkScale(w, h, rect) *
appearance.glyphFit()` 必须原样存在；`glyphFit()` 体内必须仍有 `Prefs.clamp(glyphScale, Prefs.MIN_GLYPH_SCALE,
Prefs.MAX_GLYPH_SCALE)` 与 `/ 100f;`；`TrioAppearance` 的构造必须仍从 `c.glyphScale` 取值。三条界限
（`MIN` / `MAX` / `DEF_GLYPH_SCALE`）由正则**从 `Prefs.java` 读出**再注入生成的 `Bounds.java`，不手抄，
并断言 `max > min`、默认值落在区间内。

**负控实测（七条，每条先 `Copy-Item $f "$f.bak"`、事后回滚；退出码取自 `Start-Process -PassThru` 的
`$p.ExitCode`，不取 `cmd /c "… & echo EXIT=%ERRORLEVEL%"`——后者在解析期就展开，永远报 0）：**

#### 30.5.2 决策与理由

**(a) 为什么是一条独立的键，不复用 `type_weight`。** `type_weight` 驱动的是**网络类型标签**
（环内分段绘制与环外 `RelativeSizeSpan` 都按它取字重），而这两项是状态栏上的读数。把两者绑在一起
意味着「想把读数调粗」会顺手把环外的 5G 标签也改粗，反之亦然——它们之间没有任何语义联系，只是
碰巧都叫「字重」。两条设置在屏幕上离得很远，共享一个键只会让滑杆看起来在别处产生了副作用。

**(b) 为什么字重必须自己成为重同步的第五个分句。** 字重改变画面有两条路径：typeface 本身，以及它
带来的**行高**。当字号被钉在 `PERF_MIN_SIZE_RATIO` 下限时（本机默认就落在这个档位），改字重**不改变
字号**，于是既有的「文本变了没」与「尺寸变了没」两个分句都看不见它——滑杆会像死了一样，拖了没反应，
只有碰巧触发别的重排时才跳一下。`perf.weight != weight` 这一路是唯一看得见它的地方。

**(c) 为什么预留宽度必须是「读数是什么」的函数，而不是「它此刻写着什么」的函数。** 这是最初的判断。
`reserveOutRingStrip` 原先拿 `perf.getMeasuredWidth()`（**当前文本的实测宽**）求和，而
`BatteryPresence` 大约每秒发布一次新瓦数：`0.0W`（102px）与 `6.1W`（92px）之间来回时预留值就跟着跳，
每一次跳动都经 `setPadding` 重排 MIUI 的图标行，把左侧的原生图标整体推一下。设备日志里同一个文件内
预留值在 `102` 与 `108` 之间交替，是当时的现场证据。**预留是给一个会变的文本留的位置，所以它只能是
这段文本可能取到的最宽形态的函数**，而不是它当前这一帧恰好有多宽——这条结论本身是对的，`perfWidth`
也确实该这么写。
**但上机仪器化证明它不是本次跳动的成因**：`perfWidth` 在全部 28 帧里恒为 `101`（`perfLive` 在 85↔95
之间跳而答案不动），真正的成因是 teardown 路径的抢先释放，见 **§30.6**。这条修复保留——它把「文本
变宽变窄」这一类隐患彻底关掉了——只是它单独还不足以让图标静止。

**(d) 为什么 `perfWidth` 走 paint 而不是真的 layout 一段探针字符串。** 探针方案会**踏上布局这条路**，
而 `reserveOutRingStrip` 就在布局/同步的链上——为了算一个 padding 去触发一次测量，是把自己接回
要修的那个回路里。paint 度量是纯计算。代价是没算进字距（`VALUE_LETTER_SPACING = -0.04em`），
所以答案比真正画出来的宽几个像素——**这是安全的方向**：预留宁可略宽（图标离读数略远），
绝不能短（读数压在图标上）。此后只有**数字位数**还能改变预留，那是阶跃、不是闪烁。

三个各自针对一个坑的细节：①**最宽数字要问字体自己**——把十个数字各量一遍取最大，而不是假定 `'0'`
或 `'8'`（不同字体里最宽的数字不同）；②**逐行量**——`\n` 对 paint 只是一个字符，整串量会把两行加在
一起、预留出两倍的实际宽度（而这两行是上下叠的，不是并排的）；③`(int) Math.ceil(width)` 向上取整，
不给自己留一个「小数被截掉所以偶尔短一像素」的口子。

### 30.6 充电功率修复与图标右跳的真正成因（上机仪器化定案）

这一节记的是设备回到 USB 之后做的两件事：把「充电时一直显示 `0.0W`」修掉，以及把 §30.5 猜错的
跳动成因重新定案。

#### 30.6.1 `wattsOf` 的符号：负电流才是充电

**现象**：插着充电器时状态栏长期停在 `0.0W`，偶尔蹦出 `0.6W` / `1.3W` / `5.3W`。

**实测**（`su -c 'cmd battery get -f current_now'`，USB powered / status charging / 电量 68%）：
连采 8 次**全部为负**——`-115000`、`-174000`、`-199000`、`-249000`、`-179000`、`-199000`、`-174000`、
`-204000` µA；另一轮 6 次里只有一次正值 `134000`。`charge_counter` 同期从 `2540000` 涨到 `2546000`，
证明电池**确实在充**。**⇒ 本平台充电时 `current_now` 为负，与 AOSP 的正号约定相反。**

旧的 `wattsOf` 末尾是 `final float watts = currentMicroAmps * (voltageMilliVolts / 1000f) / 1000000f;
if (!(watts > 0f)) { return 0f; } return watts;`，把负电流判成「在放电」折成 0——于是每一个真实的充电
电流都变成 `0.0W`，只有采样抖动恰好落在正值上时才显示一次真数。**这是符号约定错误，不是显示问题。**

**修法**：`return Math.abs(currentMicroAmps) * (voltageMilliVolts / 1000f) / 1000000f;`，两条不可用
分支仍返回 `TrioState.POWER_UNKNOWN`（`Float.NaN`），真零仍是真零。用幅值而不是保留 clamp，是因为
符号本身不可移植（别的平台同一情形答正），幅值才是真正在流动的电流；调用方本来就只在接充电器时绘制。

**上机确认**：重建重装、`killall com.android.systemui`、广播 `--ez perf_power true --ez debug_log true`
后日志四帧全为 `performance: "1.3W" size=33.600002 view=82x44 at 319,22 anchor=407..491 container=491x88`
（`33.600002 = base 42 × perf_scale_pct 80`），截图见 `work\verify6\w1_sb.png` 的 `1.3W`。
`tests\battery-presence.ps1` 同步改了四条用例并加两条源码守卫（必须含 `Math.abs(currentMicroAmps)`、
不得含 `if (!(watts > 0f))`），44 条全绿；两条负对照（换回旧式 / 保留字面量但改回带符号运算）
分别被源码守卫与执行级用例拦下，`PROBE_EXIT=1`。

#### 30.6.2 图标右跳的真正成因：teardown 路径的抢先释放

**先排除的**：`perfWidth` 本身。加了一段临时诊断把 `reserveOutRingStrip` 的每个分量打出来，
在广播后 20 s 的窗口里 **`perfW=101` 与 `total=107` 全部 28 帧完全恒定**，而 `perfLive`（视图实测宽）
在 85↔95 间跳、`perfText` 在 `"1.4W"/"1.3W"/"1.0W"/"1.1W"` 间跳。**⇒ §30.5(c) 猜的方向对、但对象错**：
`perfWidth` 早就把这一类关掉了，它不是本次跳动的来源。

**真正的证据**：同一份日志里 `pad=0/107` 与 `pad=0/0 saved=none` 交替出现，`strip release` 14 次、
`reserved … 0/0 -> 0/107` 14 次，**约每 1.4 s 一轮**（正是功率更新的节奏）。⇒ 图标行的 paddingEnd 在
**107 ↔ 0 之间乒乓**，整排原生图标随之横移 107px 再弹回。给 `releaseOutTypeSpace` 的诊断补上调用者后：

```
4x strip release: caller=removeOutTypeLabel icons=48981932  pad 0/107 -> 0/0 w=403
4x strip release: caller=removeOutTypeLabel icons=142978657 pad 0/107 -> 0/0 w=403
```

**根因**：`removeOutTypeLabel(View container)` 与 `removePerfLabel(View container)` 的第一步都是
`releaseOutTypeSpace(group);`，**排在 `findOutTypeLabel` / `findPerfLabel` 判空之前**；视图为 null 时
直接 `return`，**不再重新 reserve**。这两个方法在每次 sync 都会被调用（环外类型默认关闭，所以
「根本没有 label」是常态路径），紧接着 `reserveOutRingStrip` 又把 total 重新 reserve，
于是 padding 每轮 `107 → 0 → 107`。两条路径的注释都写着「先交还再提前返回，因为没挂载过的视图也可能
留下过 padding」——动机是陈旧 padding 兜底，但它没有兜底能力：`reserveOutRingStrip` 自己就是权威
（按实际 VISIBLE 的视图求和，`total <= 0` 时它会调 `releaseOutTypeSpace`）。

**修法**：两个方法都改成「判空 → 只在非 null 时 `removeView` → 无条件 `reserveOutRingStrip(group);`」，
删掉抢先的 `releaseOutTypeSpace` 与提前 return。

**上机确认**：重建重装后同一窗口里 **`strip release` 计数 = 0**，`out type: reserved` 一行都不再打印
（`reserveOutTypeSpace` 只在 padding 真要变时才打），而 `performance:` 帧照旧在变
（`"1.1W"` → `"1.2W"` → `"1.3W"` → `"1.4W"` → `"1.5W"`）。逐帧像素测量 14 张
（`work\jump5\q01..q14.png`，判据 `R,G,B < 130`，x 600..1200）：**左侧原生图标在所有帧里钉在
`832-844|846-878|890-927`，读数右缘钉在 `991-1031`，电池环钉在 `1066-1097`**——同一份窗口里读数文本
在 5 个值之间变而图标一动不动。

**探针**：这条修复原先**零覆盖**。`tests\perf-layout.ps1` 补了一组源码契约钉（对
`removeOutTypeLabel` / `removePerfLabel` 两个方法体各断言一次）：**禁止**体内出现 `releaseOutTypeSpace(`，
**要求**出现 `reserveOutRingStrip(`。负对照把抢先释放改回去（用 CRLF 容忍的正则插入，因为
`TrioHooks.java` 是 CRLF 而非 LF，字面量拼接匹配不到），探针以
`removeOutTypeLabel still releases the strip before it knows what is mounted` 退出、`PROBE_EXIT=1`；
`git checkout` 式还原后再跑 `PASS: 76 cases`。

**顺带一条教训**：`Get-Content -Raw` 往返会按 PS 5.1 的 ANSI 代码页改写非 ASCII 字节（§30.5.1 末尾），
本轮改文件一律用 `[System.IO.File]::WriteAllText(..., UTF8Encoding($false))`，并且用
`.bak` 副本而不是 `Get-Content` 做负对照回滚。

## 32. 第三十轮：#28 / #33 的遮挡修复（移植 PR #29 的 `PRIVATE_FLAG_TRUSTED_OVERLAY`）

> **本节是历史记录。** 第十七轮（§33）把整条独立窗口路线删掉了 —— `TrioOverlay.java`、

> 补丁连同它要解决的问题一起消失。下面记的判断仍然成立：那个窗口之所以被平台当成可疑覆盖层，
> 根因是**窗口类型不在白名单里**（2017 有、2041 没有），而不是窗口太大。**只要还在建窗口，就永远
> 要跟那份白名单和这套遮挡判定打交道** —— 这正是改用槽的直接理由。

用户原话：**「#28/#33 遮挡问题先修吧」**。

### 32.1 症状与两个 issue

- **#28**（2026-10-08，7 条评论）：正文只有一张截图，标题「启用模块可能会导致这样」。
- **#33**（2026-10-13，0 条评论）：一句话 ——「最新此模块，会引起LSPosed由于某个应用遮挡了权限请求界面，

  issue 里给出的临时绕法是关掉 LSPosed 的「点按劫持缓解」，或者关掉本模块的「独立窗口绘制」；

### 32.2 根因

维护者 aodianjun 在 #28 里的诊断（要点照抄）：

> 「独立窗口绘制」用的是系统级的 overlay 窗口类型（`STATUS_BAR_SUB_PANEL`，层级比通知栏还高），而且
> 窗口的 `params.alpha` 跟着宿主视图走、通常是完全不透明的。平台因此把它当成「可能劫持触摸的覆盖层」：
> 落在它下面的触摸会被标记为 obscured，带防护的应用检测到这个标记后就拒绝响应……给这个窗口打上
> `PRIVATE_FLAG_TRUSTED_OVERLAY`，平台就不再把它算作可疑覆盖层。它本来也不该被算：窗口不可触摸
> （`FLAG_NOT_TOUCHABLE`）、只有一个图标宽、位置在状态栏里，而且属于 SystemUI。

AOSP 侧证（下载 `android-14.0.0_r1` 的四个文件核对，全部为真）：

| 位置 | 事实 |
| --- | --- |
| `WindowManager.java:3176` | `public static final int PRIVATE_FLAG_TRUSTED_OVERLAY = 1 << 29;` |
| `WindowManager.java:3373` | `public int privateFlags;` —— `@hide`，`android.jar` 的 stub 里被剥掉 |
| `WindowManager.java:4366` | `public void setTrustedOverlay()`，同样 `@hide`（还要 `INTERNAL_SYSTEM_WINDOW`） |
| `WindowState.java:1197-1203` | `shouldWindowHandleBeTrusted(...)` 要求 `(privateFlags & PRIVATE_FLAG_TRUSTED_OVERLAY) != 0 && s.mCanAddInternalSystemWindow` |
| `WindowState.java:1116` | 上面那个返回值交给 `mInputWindowHandle.setTrustedOverlay(...)` |
| `WindowManagerService.java:8819-8822` | 该位被转成 `InputConfig.TRUSTED_OVERLAY` ⇒ **确实经 Binder 到服务端** |
| `WindowState.java:1205-1213` | `getTouchOcclusionMode()`：状态栏类型不是 system-alert 类型时走 `BLOCK_UNTRUSTED` |

**★ 主线为什么恰好中招**：`InputMonitor.java:740-753 isTrustedOverlay(int type)` 的类型白名单里
**有 `TYPE_STATUS_BAR_ADDITIONAL`（2041），没有 `TYPE_STATUS_BAR_SUB_PANEL`（2017）**；而本模块的
`TrioOverlay.windowType()` 恰恰**优先取 2017**（`98a5a8f`，PR #22 引入，理由是 MIUI 的 `StatusBar1`
会在配置变更/SystemUI 重启时重加并盖住 2041）。也就是说主线挑中的正是那个「既不被类型白名单豁免、
又落在 `BLOCK_UNTRUSTED` 里」的类型 —— 私有位是唯一的补救。设备侧旧 dump（`.tmp\iss21\full.log`）
里 `TRUSTED_OVERLAY` 有 427 处命中（形如 `NOT_FOCUSABLE | TRUSTED_OVERLAY`），说明这台机器（houji /
API 37）确实认这个位。

### 33.1 为什么是这条路

- **窗口路线是几何上的冗余**：三条 A/B 实测（桌面 / 锁屏 / 下拉，各拍窗口开与关两臂）显示像素差

### 33.4 教训

- **A/B 之前必须先确认当前是哪一行**：早前一次「窗口开 vs 关」的 A/B 得出了「两臂像素完全相同」
  的错误结论，原因是设备停在锁屏，而 `isStatusBarHost()` 沿 parent 链遇到名字含 `Keyguard` 就返回
  false —— 两臂**都没有**资格开窗口。测试点必须是 `MiuiPhoneStatusBarView` 那一行（唤醒 + 解锁 +
  回桌面）。
- **从像素反推病因会走错**：本仓历史上曾从像素反推出「3–8px 位移」，实际是 107px 的整行横移被
  状态栏边界裁掉之后的残影。**先把分量打出来再下结论。**
- **`[System.IO.File]`/`[System.IO.Directory]` 的相对路径按进程 CWD 解析**，而不是 PowerShell 的
  `Set-Location`：在 worktree 里做脚本手术时必须传**绝对路径**，否则会读写到主仓（本次已误伤一次，
  只能 `git checkout --` 恢复）。
- **行号手术不安全**：用「读全部行 → 按下标删除 → 写回」时，若操作前后行号基准不一致就会删错区间。
  **逐条用 `edit` 做锚定字符串替换。**
- **工作树里的 `work\<name>\` 是指向主仓的 Junction，跑工装必须走工作树根下的 `work\verify-<name>.ps1`**：
  前者内容是主仓版本（`$Root = 'C:\code\HyperDuo'`），跑它会静默地**测主仓源码**；只有后者的
  `$Root` 指向 `work\drawable`。两者行数相同、只有那一行和输出路径不同，`Get-FileHash` 一比才发现。
  另外这批脚本**不依赖 PATH**（自己找 `.tools\jdk`），但 `tests\*.ps1` 在 PATH 里没有 `javac` 时会
  静默退化成调用裸 `javac`；经由 `cmd` 传给它们完整 PATH 更稳。
- **`%ERRORLEVEL%` 在 `cmd /c` 一行内是解析期展开的**，所以 `... & echo EXIT=%ERRORLEVEL%` 读到的是
  展开时的旧值，会给出**假的 EXIT=0**。要读真实退出码，必须让 PowerShell 看 `cmd /c ...` 的
  `$LASTEXITCODE`，或把 `%ERRORLEVEL%` 写进另一个 `cmd /c` 里。
